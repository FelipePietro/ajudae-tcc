# Ajudae V1 — auditoria pré-deploy e roteiro de homologação Railway

Estado deste documento: **preparação local, sem deploy**. Branch de referência `feat/ajustes-pre-deploy`; não usar esta revisão como autorização para publicação. O backend permanece Laravel + Sanctum + MySQL; Railway Storage Bucket S3 privado é o destino preparado para novos uploads, e certificados PDF são gerados em memória sob demanda. Ver [configuração S3](railway-storage-s3.md).

## Execução PHP 8.4 preparada (não implantada)

Estratégia única: **Railpack nativo com FrankenPHP/Caddy**, configurado em [`railpack.json`](../railpack.json). O Railpack reconhece `composer.json`/`artisan`, obtém PHP 8.4 de `composer.json` (`^8.4`, também fixado como série `8.4` no overlay), instala dependências do `composer.lock` com `COMPOSER_NO_DEV=1` e serve `/app/public`. O processo HTTP é o `docker-php-entrypoint` do FrankenPHP com o Caddyfile gerado pelo Railpack. Esse Caddyfile escuta em `:{$PORT:80}` em todas as interfaces; no Railway, confirmar a porta real injetada e o domínio HTTPS. O web root é **somente** `public/`; `.env`, `vendor/` e `storage/` não são document roots. Logs do Caddy vão para stderr; configurar `LOG_CHANNEL=stderr` para os logs do Laravel. Não há `Dockerfile`, `Procfile`, `railway.json` nem comando `php artisan serve` de produção.

O start padrão do Railpack para Laravel executa `php artisan migrate --force`, `storage:link` e `optimize`. Por isso o overlay **substitui** esse start por somente FrankenPHP: não executa migration, seed, setup, scheduler, limpeza, link de storage nem cache de configuração no start. O build substitui os comandos de cache padrão por preparação de diretórios graváveis, `package:discover` e `npm run build`. Isto é necessário porque as rotas web atuais usam closures (incompatíveis com `route:cache`), o cache de configuração no build poderia congelar secrets/configurações erradas e as views Blade atuais usam `@vite`. Dependências Node de build são transitórias; `public/build` deve existir na imagem final. Nada do build pode invocar `composer run setup` (esse script contém `migrate --force`). O único estado local gravável exigido é `storage/` e `bootstrap/cache/`, **efêmero**; uploads duráveis vão aos discos S3 privados. Não usar `storage:link` para expor documentos ou imagens privadas.

Antes de autorizar deploy, inspecionar o plano/build Railpack efetivo: PHP **8.4.x** (não 8.5), `pdo_mysql`, `gd`, `exif`, `mbstring`, `dom/xml`, `curl`, `openssl`, `fileinfo` e `zip`; executar `composer check-platform-reqs` **dentro da imagem** e confirmar que `composer.lock` foi respeitado. Configurar no serviço `RAILPACK_PHP_EXTENSIONS=pdo_mysql,gd,exif,mbstring,xml,curl,zip` (ajustar apenas se o plano mostrar nomes/instalação diferentes); OpenSSL e fileinfo podem vir integrados à imagem, mas devem ser verificados. `composer check-platform-reqs` cobre requisitos declarados pelas bibliotecas; GD, EXIF e PDO MySQL são exigências adicionais do código e precisam de checagem explícita. O Railpack CLI e um runtime/container PHP 8.4 não estavam disponíveis na revisão local; a execução real do plano e dos testes nesse runtime permanece **NÃO VALIDADA**. O build remoto, a versão efetivamente resolvida e os módulos carregados exigem confirmação humana posterior. Não criar configuração concorrente por tentativa.

`GET /up` (Laravel) e `GET /api/health` (JSON) são liveness sem consulta a MySQL/S3. Configure `/up` como healthcheck HTTP do serviço e confirme `2xx` após boot com banco ainda vazio; essa resposta **não prova readiness** de MySQL, bucket, migrations ou fluxos autenticados. Railway usa `$PORT` para o healthcheck; o Caddyfile do Railpack já o respeita. Healthcheck do Railway ocorre no início do deploy, não é monitoramento contínuo. Testar separadamente dependências e rotas protegidas na homologação. Confirmar limite HTTP/PHP de multipart acima de 10 MiB para documento e 5 MiB para imagem, com margem, sem permitir carga ilimitada indevida; medir memória da sanitização de imagem no PHP 8.4 e dimensionar o serviço. Não foram criados limites novos de upload neste bloco.

### Variáveis do futuro serviço Laravel (somente no painel Railway)

Exemplos de referências abaixo são **estruturais**: substituir os nomes `MySQL` e `BUCKET_SERVICE` pelos nomes reais exibidos no projeto; verificar os nomes disponíveis na aba Variables/Credentials. Nunca copiar valores ou as referências literais para `.env` local, documentação versionada ou ZIP.

| --- | --- | --- |
| `APP_NAME`, `APP_ENV`, `APP_DEBUG` | `Ajudae`, `production`, `false` | Sem stack trace público. |
| `APP_KEY` | segredo gerado **uma vez** e armazenado no Railway | Estável entre deploys; nunca gerar no build/start. |
| `APP_URL` | `https://<DOMINIO_PUBLICO_REAL>` | Confirmar HTTPS/URLs absolutas. |
| `DB_CONNECTION` | `mysql` | Não permitir fallback SQLite. |
| `DB_HOST` | `${{MySQL.MYSQLHOST}}` | Serviço real deve ser identificado no painel. |
| `DB_PORT` | `${{MySQL.MYSQLPORT}}` | Usar porta da conexão correspondente. |
| `DB_DATABASE` | `${{MySQL.MYSQLDATABASE}}` | Banco novo/vazio, não `ajudae_tcc` local. |
| `DB_USERNAME` | `${{MySQL.MYSQLUSER}}` | Referência secreta. |
| `DB_PASSWORD` | `${{MySQL.MYSQLPASSWORD}}` | Referência secreta. |
| `DB_URL` | **não definir** | Se existir, Laravel pode sobrepor os `DB_*`; remover conflito. |
| `DOCUMENT_PRIVATE_DISK`, `IMAGE_STORAGE_DISK` | `railway_private`, `railway_images` | Mesmo bucket privado, raízes `private/` e `images/`. |

| `AWS_*` | [tabela do bucket](railway-storage-s3.md) | Mapear nomes efetivamente expostos, sem ACL pública nem URL permanente. |
| `LOG_CHANNEL`, `LOG_LEVEL` | `stderr`, `warning` ou `info` | Inspecionar logs por PII/segredos; stderr é canal existente. |
| `CACHE_STORE`, `SESSION_DRIVER` | `database`, `database` | Tabelas `cache`, `cache_locks`, `sessions` existem nas migrations V1; só usar após migração manual. |
| `QUEUE_CONNECTION` | `sync` | Não há worker configurado nem jobs assíncronos requeridos agora. |
| `CORS_ALLOWED_ORIGINS` | origens HTTPS reais, separadas por vírgula | `config/cors.php` restringe `api/*`, sem wildcard por padrão. |
| `MAIL_MAILER` | `log` até definir entrega real | Alertas por email não devem ser presumidos entregues. |
| `RAILPACK_PHP_EXTENSIONS` | lista acima | Variável de build do Railpack; conferir extensões efetivas. |

`config/app.php` usa timezone `UTC`; não alterar esse contrato sem revisão. Em HTTPS, conferir `X-Forwarded-Proto`, geração de URLs e cookies no domínio real. `bootstrap/app.php` **não** declara proxies confiáveis customizados: avaliar a topologia/endereço do proxy Railway e testar antes de configurar trust amplo (`*` não deve ser adotado sem análise). Validar `SESSION_SECURE_COOKIE`/`SESSION_DOMAIN` para o frontend real; a API Sanctum atual usa Bearer tokens e o CORS não suporta credenciais cross-site. Os rate limits de cadastro/login usam o cache configurado; para múltiplas réplicas, usar cache compartilhado e revisar chave de IP/proxy. Não habilitar Redis nem worker sem necessidade comprovada.

### Sequência manual após revisão/autorização separadas

1. Revisar os candidatos Git e autorizar separadamente commit/push da branch `feat/ajustes-pre-deploy`. Confirmar que o código revisado está no GitHub **antes** de vincular a branch ao futuro serviço HTTP no mesmo projeto Railway do MySQL e bucket existentes. Não houve publicação nesta preparação.
2. No painel, selecionar Railpack e branch correta; não configurar start/build paralelos que sobreponham `railpack.json`. Inserir variáveis e secret references acima; gerar `APP_KEY` uma vez; escolher domínio HTTPS, memória/recursos e healthcheck `/up`. Verificar plano de build, versão/extensões e logs; nenhum segredo deve aparecer em artefatos ou saída.
3. Confirmar diretamente que o MySQL de homologação é novo e vazio, com backup/limites conhecidos. Executar `php artisan migrate --force` como **ação explícita única inicial** em ambiente autorizado, fora de build/start/cron. As 12 migrations antigas modificadas são parte do schema inicial oficial V1 do TCC e as migrations novas completam esse schema; não criar migração histórica para o MySQL vazio. Seeds só com autorização e dados fictícios. Nunca usar `migrate:fresh` ou `composer run setup` no serviço persistente.
4. Com usuários/arquivos sintéticos, testar `/up`, `/api/health`, login/rota privada, CORS, upload/leitura/substituição/exclusão em `railway_images` e `railway_private`, autorização de download documental, ETag/304 de imagem e PDF de certificado sob demanda. Confirmar sem objeto PDF persistido, sem URL pública de bucket e sem exposição de secrets.
5. Não iniciar scheduler junto ao HTTP. Depois de revisar idempotência e timezone, escolher **um único** serviço cron/executor de `php artisan schedule:run` a cada minuto; manter expurgo documental `--dry-run`, exclusão de contas em preview e reconciliação de imagens somente manual. Evitar múltiplas instâncias de cron; locks precisam de cache compartilhado. Não há worker de fila neste bloco.
6. Observar logs e recursos sem PII/segredos, checar backup e restauração separadamente, e preparar rollback do **código** sem apagar MySQL/bucket. Reverter código não desfaz schema; validar compatibilidade antes do rollback. Entregar URL REST e [guia de integração](guia-integracao-api.md) ao grupo só depois de homologação passar.

Pendências bloqueantes para declarar deploy pronto: teste real de PHP 8.4/FrankenPHP e plano Railpack; build de assets/rotas na imagem; conexão Railway MySQL e S3 real; HTTPS/proxy/domínio/CORS; memória e upload; smoke tests e concorrência real; autorização humana de commit, publicação e operações remotas. Esta revisão não acessa infraestrutura Railway.

Limite de frontend conhecido: `vite.config.js` compila apenas `resources/css/app.css` e `resources/js/app.js`, enquanto algumas views Blade referenciam também `cadastro_ong.css`, `editar_ong.css`, `painel_ong.css` e `perfil_ong.css` em `@vite`. Essas páginas podem falhar por entradas ausentes no manifest em produção. Como este bloco proíbe editar frontend/JS, **a integração das entradas Vite fica pendente com a equipe do frontend antes de expor essas páginas**; o build de assets básicos não é uma validação completa de Blade. A API e seus healthchecks não dependem dessas views.

## Riscos encontrados e tratamento

| Severidade | Evidência local | Situação/ação mínima |
| --- | --- | --- |
| Crítica | A migration original de `certificado` foi editada retroativamente. A versão anterior comprovada no ZIP operacional tinha `inscricao_id`, `codigo`, `arquivo_path`, `disponibilizado_em`; a atual espera `evento_id`, `pessoa_id`, `codigo_verificacao`, `total_minutos`, nomes congelados e `emitido_em`. | Migration evolutiva nova detecta schema atual ou legado exato. Em tabela legada **vazia**, evolui sem remover colunas antigas. Havendo certificados legados, interrompe antes do primeiro DDL: horas e nomes congelados não são recuperáveis com segurança a partir do schema antigo. Decisão humana e backup são obrigatórios. |
| Alta | Upload de imagem gerenciada gravava bytes originais, incluindo EXIF/GPS de JPEG e metadata PNG/WebP, em imagem servida publicamente. | Sanitização antes de persistir: JPEG reencodificado com orientação aplicada; PNG/WebP retêm chunks essenciais e removem metadados textuais/EXIF/XMP/ICC. Links legados externos permanecem fora desse tratamento. |
| Alta | 5 MiB comprimidos podem consumir centenas de MiB ao decodificar 25 MP. | Pré-checagem de memória antes do decode, mantendo limites de 5 MiB/8.000 px/25 MP. No PHP local de 512 MiB, imagens extremas podem ser rejeitadas com erro controlado; dimensionar memória do serviço Railway e testar no runtime alvo. Não há garantia de pico para todos os codecs/arquivos. |
| Alta | Expurgo documental estava agendado em modo efetivo diariamente; exclusão de contas e reconciliação de imagens também podiam remover dados/objetos automaticamente. | Expurgo e exclusão de contas são apenas `--dry-run`; reconciliação de imagens foi retirada do agendamento. Habilitação real exige política, backup e aprovação. |
| Média | Não havia configuração CORS própria para origens de frontend separadas. | `config/cors.php` permite somente origens explícitas de `CORS_ALLOWED_ORIGINS`; nenhum curinga/credenciais cross-site por padrão. Origem real ainda precisa ser definida. |
| Média | Cadastro/login expostos sem limite de taxa específico. | Rotas de Pessoa/ONG limitadas a 5 cadastros/min e 10 logins/min por chave do middleware. Ainda requer verificação por IP/proxy e compartilhamento de cache em escala. |
| Média | GET de imagem repetia transferência integral para cada requisição. | `ETag` por chave gerenciada e `304` em `If-None-Match`, com cache público de 5 min e URL versionada. O servidor ainda lê o objeto inteiro em até 5 MiB quando devolve `200`; streaming seria otimização posterior mensurável, não requisito bloqueante. |
| Alta, pendente | Documentos já gravados no disk local podem ficar inacessíveis em filesystem efêmero Railway. | Inventariar referências `storage_disk=local`, copiar/validar objetos privados para S3 e atualizar referências com plano de rollback antes de desativar disco persistente. Não copiar dados reais nesta tarefa. |
| Alta, pendente | Bucket Railway já existe, mas não foi conectado nem testado com a API; não há runtime PHP 8.4 local verificado. | Configurar referências de variáveis manualmente, testar PHP 8.4, HTTPS, permissões do bucket, proxy e fluxos em homologação antes de declarar pronto. |

## Certificados: política de evolução

O schema anterior está comprovado pela cópia de `database/migrations/2026_10_08_000000_create_governance_tables.php` no ZIP operacional de 12/10/2026. Sua tabela `certificado` tinha PK `certificado_id`, FK/unique `inscricao_id`, unique `codigo`, `arquivo_path` nullable, `disponibilizado_em` nullable e timestamps. O schema atual é construído pela versão editada dessa mesma migration, por isso `migrate:fresh` sozinho não representa upgrade.

A migration `2026_10_15_000000_upgrade_legacy_certificado_schema.php` é no-op em schema atual, falha explicitamente em schema parcial/desconhecido e faz evolução apenas quando a tabela legada está vazia. As colunas legadas são mantidas para preservar compatibilidade/inspeção, ficando `inscricao_id` e `codigo` nullable; os campos novos seguem o contrato atual. **Não** inventa certificados históricos, códigos, carga horária ou nomes, nem recalcula XP. `down()` não apaga nada: em MySQL DDL pode ter commit implícito, e rollback seguro requer backup/restauração coordenada. Uma base com certificados legados precisa de decisão sobre migração histórica assistida antes de executar `php artisan migrate --force`.

Antes de migrar um banco persistente, comparar a tabela `migrations`, schema real, índices/FKs e contagem de `certificado` com este diagnóstico. Fazer backup verificável e ensaio de restauração. Não usar `migrate:fresh`, `db:wipe` nem seed de demonstração em dados persistentes. Outras migrations antigas aparecem modificadas no working tree; a equivalência entre cada schema já implantado e as versões atuais **não foi comprovada** por snapshots de produção. Inventariar a tabela `migrations` e schema da homologação/produção antes de qualquer migração, sem presumir que apenas certificados divergem.

## Preparação local e variáveis

Medição reproduzível local: gerar PNG sintético uniforme de 8.000 × 3.125 px (25 MP) com GD em PHP 8.5.5/512 MiB produziu ~79 KiB comprimidos e pico PHP de **205.520.896 bytes** apenas na geração; o teste do serviço confirmou rejeição controlada antes do decode quando `memory_limit=128M`. Esse pico não é uma medição de requisição real no Railway nem cobre todos os codecs.

1. Revisar diff e dependências (`composer audit --locked`, `composer check-platform-reqs`), sintaxe, testes MySQL e migrations novas. Não levar `.env`, credenciais, dumps, logs, ZIPs ou banco de testes ao Git/deploy. Exigir PHP **8.4+ compatível com `composer.json` e lock**, extensões necessárias (incluindo PDO MySQL, GD, EXIF, mbstring e as requeridas por Laravel, DomPDF e Flysystem/S3). O teste local em PHP 8.5.5 não substitui smoke test em PHP 8.4.
2. Escolher domínio HTTPS da API e origens exatas do frontend. Configurar `APP_ENV=production`, `APP_DEBUG=false`, `APP_KEY` persistente e secreto, `APP_URL=https://...`, `CORS_ALLOWED_ORIGINS` somente com origens autorizadas. Não mudar `APP_KEY` depois de dados criptografados/tokens em uso. Definir política de proxies confiáveis conforme topologia Railway efetiva; não usar `*` sem análise. Validar scheme/redirects/URLs absolutas atrás do proxy.
3. Provisionar manualmente Railway com serviço web e MySQL persistente; mapear `DB_CONNECTION=mysql`, host, porta, nome do banco, usuário e senha como variáveis/secret references. Avaliar TLS de MySQL conforme conexão real; não assumir que conexão interna e externa exigem a mesma configuração. Nunca registrar valores em logs.
4. Usar o Railway Storage Bucket privado já provisionado; configurar `IMAGE_STORAGE_DISK=railway_images`, `DOCUMENT_PRIVATE_DISK=railway_private` e as referências de variáveis S3 conforme [guia](railway-storage-s3.md). Confirmar endpoint HTTPS, região e estilo de URL no painel, sem inventar valores. Privilégios mínimos para leitura/gravação/exclusão; sem URL pública permanente. Fazer teste real de upload/download/negação em homologação apenas após autorização separada. Testes locais com `Storage::fake` não provam integração.
5. Revisar `SESSION_DRIVER`, `CACHE_STORE`, filas e múltiplas réplicas. Para Sanctum Bearer, verificar armazenamento/revogação de tokens no MySQL. Se usar `withoutOverlapping`/locks de scheduler com várias instâncias, o cache deve ser compartilhado; não depender de cache local para coordenação distribuída. Ajustar retenção de logs sem PII/secrets.

## Build, inicialização e healthcheck

O caminho de build/start escolhido está na seção "Execução PHP 8.4 preparada" e em `railpack.json`. Não executar `route:cache` enquanto houver rotas closure, nem `config:cache` no build com variáveis potencialmente ausentes. Confirmar comportamento real do Railpack no primeiro build **apenas após autorização separada**, sem ativar migrations automáticas.

`GET /api/health` pode ser usado como healthcheck superficial sem devolver segredo ou PII; uma resposta HTTP boa não demonstra disponibilidade de MySQL/S3. Fazer checks separados, autenticados/operacionais, para dependências. Confirmar headers de erro em `APP_DEBUG=false` e limite de upload também no servidor HTTP/proxy (`client_max_body_size` ou equivalente) para 5 MiB de imagem e 10 MiB de documento, com alguma margem para multipart.

## Migração e scheduler em homologação

1. Com banco descartável de homologação ou backup e plano de restauração verificados, inspecionar migrations pendentes e schema real; só então executar `php artisan migrate --force`. Se houver certificados legados, **parar** e decidir a migração histórica assistida. Não executar migração automaticamente no start de todas as réplicas.
2. Configurar processo/serviço de scheduler para `php artisan schedule:run` a cada minuto, ou mecanismo equivalente suportado pela arquitetura escolhida. Garantir somente um executor ou cache compartilhado/lock distribuído; revisar timezone (`America/Sao_Paulo`) e idempotência. `routes/console.php` agenda alertas de antecedentes e pré-visualizações de expurgo documental e exclusão de contas. A reconciliação de imagens **não** está agendada: ela remove objetos e aguarda revisão operacional. As tarefas devem registrar falhas sem revelar paths/PII em logs.
   `schedule:list` pode consultar o cache de locks; com `CACHE_STORE=database` e variáveis DB locais erradas, até a listagem tenta acessar o banco de desenvolvimento. Em verificações locais, configurar explicitamente `APP_ENV=testing`, `DB_CONNECTION=mysql`, `DB_DATABASE=ajudae_tcc_testing`, `DB_URL=` e `CACHE_STORE=array` antes de listar tarefas. No Railway, `schedule:run` é disparo periódico; não substitui um worker de fila/serviço persistente. Esta revisão não habilita o scheduler real.
3. Testar `documentos:excluir-retidos --dry-run --limit=100` e a política de retenção usando **dados sintéticos**. Habilitar expurgo efetivo em produção somente após aprovação explícita, backup e simulação. Não rodar limpeza real desta revisão. Para imagens, observar fila `pending_image_deletions`; o comando manual `imagens:reconciliar --limit=100` verifica referências antes de remover, mas só deve ser executado após revisão. `app:excluir-contas-pendentes` está agendado com `--dry-run`; a execução sem opção também é pré-visualização e `--execute` falha deliberadamente. Cadastros normais criam aceite de termos e podem ter notificações/solicitações LGPD sem FK: não há política aprovada para apagar ou anonimizar esses registros. Definir retenção, elegibilidade e tratamento histórico antes de habilitar qualquer hard-delete.
4. Se houver filas assíncronas, definir workers/supervisão e drivers persistentes antes de ativá-las. Não pressupor que cron web e queue worker sejam o mesmo processo.

## Smoke tests externos e entrega ao frontend

- Validar URL HTTPS, `APP_DEBUG=false`, CORS de origem permitida e origem não permitida, `401/403/404/409/422`, rate limit e ausência de stack trace.
- Com contas fictícias e permissões distintas: login/logout Sanctum, perfil público/privado, workflow de validação com lock, ONG/organizador, Evento/Agenda/inscrição/presença, avaliação, XP/ranking, padrinhos e antecedentes.
- Enviar imagem sintética sem PII, confirmar bytes sanitizados, ETag/304, troca de URL na substituição e remoção; testar bucket privado indisponível sem perda da referência atual. Não fazer teste com dados reais de participantes.
- Enviar documento fictício ao S3, provar que titular/Admin autorizado baixa e terceiro recebe negativa; verificar disk concreto de cada registro. Gerar certificado PDF autorizado sob demanda e confirmar que não surgiu objeto PDF persistido.
- Observar tempo/memória em upload de 25 MP no runtime PHP 8.4 e custo de tráfego GET (cada `200` lê até 5 MiB na aplicação; `304` evita baixar os bytes). Se 512 MiB/limites do container forem insuficientes, dimensionar recurso ou decidir novo limite com o grupo; não alterar silenciosamente.
- Configurar backups automáticos/retenção e testar restauração em instância separada. Definir orçamento e alertas de uso Railway, logs e responsáveis por incidentes. Não criar recursos pagos automaticamente.

Somente após esses testes, fornecer `API_BASE_URL` e o [guia de integração](guia-integracao-api.md) ao grupo. Nenhuma URL de homologação foi criada por esta revisão.

## Rollback operacional

Interromper tráfego/escritas, preservar logs e snapshot, restaurar release anterior **junto de schema/dados compatíveis** por backup testado. Não confiar em `migrate:rollback` para desfazer a evolução de certificados: a migration `down()` é deliberadamente não destrutiva. Para objeto S3, manter referência de disk/chave e preservar backup conforme política; nunca apagar em massa para “voltar” versão. Validar integridade e somente depois reabrir tráfego.
